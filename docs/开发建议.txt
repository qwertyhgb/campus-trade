# 校园二手交易平台项目开发建议与学习方案

## 一、项目当前定位

当前项目是一个基于 Java 21 + Spring Boot 4.1.0 + MyBatis-Plus + MySQL + Redis 的校园二手交易平台，已经完成用户模块、权限模块、商品模块、分类模块、图片上传模块，订单模块的 Entity、Mapper、DTO、VO、Service、ServiceImpl 已经完成，但 OrderController 尚未实现。

当前项目已经具备 Java 后端项目的基本雏形，不再是单纯的 CRUD Demo。接下来的重点不应该是盲目添加大量新技术，而应该围绕现有项目继续打磨，目标是把项目从“能运行”升级成“能写进简历、能讲清设计、能经受面试深挖”的项目。

项目核心业务链路应该是：

```text
用户注册/登录
→ 发布商品
→ 浏览商品
→ 商品详情
→ 买家下单
→ 卖家确认/取消
→ 订单完成或取消
```

因此，当前最高优先级是补齐订单 Controller，打通完整交易闭环。

---

## 二、项目开发总原则

### 1. 先完成核心闭环，再考虑扩展功能

当前阶段不要急着做聊天、推荐、前端、Elasticsearch、RabbitMQ、Spring Cloud、K8s 等功能。
项目最核心的是交易闭环，所以优先级应该是：

```text
订单 Controller
→ 订单状态流转
→ 订单事务控制
→ 商品状态控制
→ 并发下单处理
→ 接口文档
→ 日志与异常完善
→ 搜索/收藏等轻量扩展
→ 测试、压测、部署
→ 简历化、面试化总结
```

### 2. 不要为了“技术栈好看”强行堆技术

项目中每引入一个技术，都要能回答三个问题：

```text
1. 这个技术解决了什么问题？
2. 为什么不用更简单的方案？
3. 如果不用这个技术，会有什么缺点？
```

例如：

* Redis 用于登录态存储，这是合理的；
* 自定义注解 + 拦截器实现 RBAC，这是合理的；
* MySQL 用于商品和订单数据存储，这是合理的；
* 目前强行加入 Spring Cloud 不太合理，因为项目仍是单体架构；
* 目前强行加入 RabbitMQ 也不是必须，除非有明确异步场景；
* 目前强行加入 Elasticsearch 不是必须，可以先用 MySQL LIKE 实现搜索。

项目不是技术博物馆，不是摆满工具就高级。真正高级的是：每个设计都有理由。

## 三、第一阶段：补完订单模块，打通交易闭环

### 阶段目标

完成 OrderController，实现订单模块对外接口，使项目具备完整的交易流程。

### 建议实现接口

| 接口   | 方法   | 路径                   | 权限        | 说明         |
| ---- | ---- | -------------------- | --------- | ---------- |
| 创建订单 | POST | /orders              | 登录用户      | 买家对商品下单    |
| 确认订单 | PUT  | /orders/{id}/confirm | 卖家        | 卖家确认交易     |
| 取消订单 | PUT  | /orders/{id}/cancel  | 买家/卖家     | 取消订单       |
| 订单详情 | GET  | /orders/{id}         | 买家/卖家/管理员 | 查询订单详情     |
| 我买到的 | GET  | /orders/buyer        | 登录用户      | 查询我作为买家的订单 |
| 我卖出的 | GET  | /orders/seller       | 登录用户      | 查询我作为卖家的订单 |

### 创建订单时必须校验

创建订单不是简单 insert，一定要有业务校验：

```text
1. 用户必须登录；
2. 商品必须存在；
3. 商品必须处于可购买状态；
4. 用户不能购买自己发布的商品；
5. 商品不能已经被别人下单；
6. 创建订单时要记录 buyerId、sellerId、productId、price、status；
7. 创建订单后要修改商品状态，防止别人继续购买；
8. 整个下单过程必须加事务。
```

### 订单状态建议

订单状态不要只用 0、1、2 这种魔法数字，建议用枚举或者常量表达清楚。

```text
PENDING：待确认
CONFIRMED：已确认
CANCELED：已取消
COMPLETED：已完成，可选
```

### 商品状态建议

商品模块最好配合订单模块增加状态流转。

```text
ON_SALE：在售
OFF_SALE：下架
LOCKED：已被下单，待确认
SOLD：已售出
```

### 推荐状态流转

```text
商品初始状态：ON_SALE

买家下单：
ON_SALE → LOCKED
订单状态：PENDING

卖家确认：
LOCKED → SOLD
订单状态：CONFIRMED

买家或卖家取消：
LOCKED → ON_SALE
订单状态：CANCELED
```

### 订单模块需要重点学习的内容

#### 1. 事务

订单模块必须学习事务，因为创建订单和修改商品状态必须保证一致性。

需要掌握：

```text
1. @Transactional 的基本使用；
2. 事务为什么能保证数据一致性；
3. 什么情况下事务会失效；
4. 方法内部调用为什么事务可能失效；
5. 异常被 catch 后事务为什么可能不回滚；
6. 默认情况下哪些异常会触发回滚；
7. 下单、取消、确认这些方法为什么需要事务。
```

重点理解：

```text
创建订单成功，但商品状态修改失败，这种情况是不允许的。
商品状态修改成功，但订单创建失败，这种情况也是不允许的。
所以这两个操作要放在同一个事务里。
```

#### 2. 并发安全

校园交易平台虽然是练习项目，但订单下单天然涉及并发问题。
例如两个用户同时购买同一个商品，如果不处理，就可能出现“一件商品卖给两个人”的问题。

推荐使用简单可靠的条件更新方案：

```sql
UPDATE product
SET status = 'LOCKED'
WHERE id = ? AND status = 'ON_SALE'
```

如果影响行数为 1，说明当前用户抢到了商品。
如果影响行数为 0，说明商品已经被别人下单或状态不允许购买。

这个方案比一上来使用复杂分布式锁更适合当前项目，简单、可靠、容易讲清楚。

需要掌握：

```text
1. 什么是并发下单；
2. 为什么普通查询后再更新会有并发问题；
3. 什么是条件更新；
4. 为什么 UPDATE ... WHERE status = 'ON_SALE' 可以防止重复下单；
5. 什么是乐观锁思想；
6. 什么情况下需要悲观锁；
7. 什么情况下才需要 Redis 分布式锁。
```

#### 3. 幂等性

下单、取消订单、确认订单都要考虑重复请求。

例如：

```text
用户连续点击两次下单按钮；
用户重复点击取消按钮；
前端网络重试导致同一个请求发送多次；
接口被恶意重复调用。
```

需要考虑：

```text
1. 同一个用户对同一个商品不能重复创建订单；
2. 已取消订单不能再次取消；
3. 已确认订单不能再次确认；
4. 已售出商品不能再次下单；
5. 订单状态流转必须有合法性校验。
```

推荐做法：

```text
1. 下单前检查商品状态；
2. 下单时使用条件更新；
3. 订单状态变更前判断当前状态是否合法；
4. 必要时增加唯一索引，例如 product_id 在未完成订单中不能重复。
```

## 四、第二阶段：强化用户与权限模块

当前项目已经有：

```text
@PublicApi
@RequireRole
LoginInterceptor
RoleInterceptor
Redis Token 登录态
UserHolder ThreadLocal
BCrypt 密码加密
```

这是一个很好的学习点，必须打磨成面试亮点。

### 用户登录流程建议整理成文档

建议写成如下流程：

```text
1. 用户提交用户名和密码；
2. 后端根据用户名查询用户；
3. 使用 BCrypt 校验密码；
4. 校验成功后生成 Token；
5. 将 Token 作为 key，将用户信息存入 Redis Hash；
6. 设置 Token 过期时间；
7. 返回 Token 给前端；
8. 前端后续请求在请求头中携带 Token；
9. LoginInterceptor 从请求头中获取 Token；
10. 根据 Token 查询 Redis；
11. 如果 Redis 中存在用户信息，则将用户信息存入 UserHolder；
12. Controller 和 Service 可以通过 UserHolder 获取当前用户；
13. 请求结束后清理 ThreadLocal，避免内存泄漏。
```

### 需要学习的内容

#### 1. Redis 登录态

需要掌握：

```text
1. 为什么登录态可以放 Redis；
2. Token 和 Session 的区别；
3. Redis Hash 怎么存用户信息；
4. Redis TTL 有什么作用；
5. 登出时为什么要删除 Redis 中的 Token；
6. 如何实现 Token 自动续期；
7. Redis 宕机会对登录产生什么影响。
```

#### 2. ThreadLocal

UserHolder 是一个非常重要的面试点。

需要掌握：

```text
1. ThreadLocal 是什么；
2. 为什么可以用 ThreadLocal 保存当前登录用户；
3. ThreadLocal 在线程池环境下有什么风险；
4. 为什么请求结束后必须 remove；
5. 如果不 remove，会导致什么问题；
6. ThreadLocal 和普通静态变量有什么区别。
```

### 推荐面试表达

```text
我的项目没有直接引入完整 Spring Security，而是使用自定义注解 + 拦截器实现轻量级 RBAC 权限控制。这样可以让我更清楚地理解认证和授权的底层流程。用户登录成功后，系统生成 Token 并将用户信息存入 Redis，后续请求通过 LoginInterceptor 校验 Token，并将当前用户信息放入 ThreadLocal，方便业务层获取当前用户。请求结束后会清理 ThreadLocal，避免线程复用导致用户信息污染。
```

## 六、第四阶段：强化 Redis 能力

当前 Redis 主要用于登录会话存储。这个场景是合理的，但可以继续加深。

### 当前 Redis 使用场景

```text
Token → 用户信息 Hash
登录态校验
登出删除 Token
Token 过期控制
```

### 可以继续增强的 Redis 场景

#### 1. 登录 Token 自动续期

每次用户访问接口时，如果 Token 有效，可以刷新过期时间。

```text
用户持续活跃：Token 不过期
用户长期不访问：Token 自动过期
```

#### 2. 商品详情缓存

可以将热门商品详情缓存到 Redis。

流程：

```text
查询商品详情
→ 先查 Redis
→ Redis 有数据，直接返回
→ Redis 没数据，查 MySQL
→ MySQL 查询结果写入 Redis
→ 返回数据
```

#### 3. 防止缓存穿透

如果商品不存在，不要让大量请求一直打到数据库。
可以缓存空值，并设置较短过期时间。

#### 4. 防止缓存击穿

如果某个热门商品缓存突然过期，可能大量请求同时打到数据库。
可以使用互斥锁或逻辑过期方案。

### 需要学习的 Redis 内容

```text
1. Redis 常用数据结构；
2. String、Hash、List、Set、ZSet 的使用场景；
3. Redis 为什么快；
4. Redis 是单线程吗；
5. Redis 6.0 多线程主要处理什么；
6. Redis 缓存穿透；
7. Redis 缓存击穿；
8. Redis 缓存雪崩；
9. Redis 分布式锁；
10. Redisson 看门狗机制；
11. Redis 和 MySQL 的数据一致性；
12. RDB 和 AOF；
13. Redis 主从、哨兵、集群的基本概念。
```

### 当前项目最应该掌握的 Redis 面试点

```text
1. 为什么使用 Redis 存登录态？
2. Token 过期时间怎么设置？
3. 用户登出后 Token 怎么失效？
4. Redis 中用户信息用什么结构存？
5. Redis 宕机后用户登录会受到什么影响？
6. 商品详情适不适合缓存？
7. 如何防止缓存穿透？
8. 如何保证 Redis 和 MySQL 数据一致性？
```

### 6. DTO、VO、Entity 分层

需要理解为什么不能直接把 Entity 暴露给前端。

推荐理解：

```text
Entity：
数据库表结构映射。

DTO：
前端请求参数对象。

VO：
后端返回给前端的视图对象。
```

好处：

```text
1. 避免数据库字段直接暴露；
2. 避免前端传入不该修改的字段；
3. 提高接口可维护性；
4. 不同接口可以返回不同 VO；
5. 数据库结构变化不一定影响接口结构。
```

可以这样设计接口：

```text
GET /products/search?keyword=电脑&categoryId=1&page=1&pageSize=10&sort=price
```

学习重点：

```text
1. LIKE 查询；
2. 分页查询；
3. 条件查询；
4. 动态 SQL；
5. 索引设计；
6. LIKE 查询的局限性；
7. 什么时候需要 Elasticsearch。
```

面试表达：

```text
当前项目数据规模较小，所以先使用 MySQL LIKE 实现基础搜索。后续如果商品数量变大，或者需要更好的分词搜索、相关性排序，可以引入 Elasticsearch。
```

### 2. 收藏模块

收藏模块简单实用，适合练表设计和唯一索引。

新增表：

```text
favorite
id
user_id
product_id
created_time
```

建议加唯一索引：

```sql
CREATE UNIQUE INDEX uk_user_product ON favorite(user_id, product_id);
```

功能接口：

```text
POST /favorites/{productId}：收藏商品
DELETE /favorites/{productId}：取消收藏
GET /favorites：我的收藏列表
GET /favorites/{productId}/status：查询是否已收藏
```

学习重点：

```text
1. 多对多关系；
2. 唯一索引；
3. 防重复收藏；
4. 幂等性；
5. 分页查询；
6. 商品删除后收藏如何处理。
```

### 3. 消息/聊天模块

短期不建议直接做实时聊天。
WebSocket 会引入比较多额外复杂度，容易让项目膨胀。

更推荐先做“站内留言”：

```text
买家可以给商品留言；
卖家可以回复留言；
用户可以查看我的消息；
消息可以标记已读。
```

这样比实时聊天更简单，也更适合当前阶段。

### 4. RabbitMQ 是否需要加入

当前项目暂时不需要强行加入 RabbitMQ。
后续有明确异步场景时再加入。

合理场景：

```text
1. 下单成功后异步发送站内消息；
2. 订单超时未确认自动取消；
3. 图片上传后异步压缩；
4. 商品审核结果异步通知；
5. 系统通知异步发送。
```

不合理场景：

```text
普通新增商品强行发 MQ；
普通查询商品强行发 MQ；
只是为了简历写“使用 RabbitMQ”。
```

推荐后期可以做：

```text
订单超时未确认自动取消。
```

先用定时任务实现，后续再升级为 RabbitMQ 延迟队列。

不要把目标定成“我要做一个超级复杂的平台”。
当前阶段更现实、更有价值的目标是：

```text
我要把这个校园交易平台打磨成一个结构清晰、业务闭环完整、技术点真实、面试能讲的 Java 后端项目。
```

当前项目最应该围绕“订单交易 + 权限控制 + Redis 登录态 + MySQL 索引 + 工程规范”继续深入。
